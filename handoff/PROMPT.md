## 진행 방식
1. SPEC.md 전체를 읽고 10줄 이내로 요약한다. 모호한 점은 질문하지 말고 가장 합리적인 해석으로 진행하며 docs/decisions.md에 기록한다.
   사용자에게 묻는 것은 사용자만 할 수 있는 일(비밀 값 입력, 계정·권한, 아티팩트 게시 승인, 공유·초대)뿐이다.
2. SPEC 12장의 단계 순서로 진행한다. 단계 사이에 멈춰서 확인을 기다리지 않는다.
3. PROGRESS.md에 단계별 체크리스트를 만들고, 항목 하나를 끝낼 때마다 체크하고 커밋한다(항목 하나 = 커밋 하나). 중간에 끊겨도 PROGRESS.md만 보고 이어 갈 수 있어야 한다.
4. 보고는 단계가 끝날 때 한 번, 짧게: 만든 것 / 확인한 범위(아래 검증 규칙의 세 단계) / 안 된 것·미검증 / 내린 결정(decisions.md 행 번호). 같은 내용을 되풀이하지 않는다.
5. 작업은 하위 에이전트 여러 개로 병렬 처리해도 된다(더 낮은 등급 모델 사용 가능). 이때 아래 "병렬 작업 규칙"을 지킨다.
6. 마지막에 SPEC 7장 완료 기준과 13장 시나리오를 표로 대조한다. 사용자가 마지막 리뷰를 생략하라고 하면 생략한다.

## 검증·보고 규칙
- 확인 범위를 세 단계로 구분해 적는다: "로컬"(로컬 모크·가짜 AI) / "실제 아티팩트"(claude.ai에 게시해 직접 확인) / "실서비스"(실제 배포 주소·실제 API).
- 확인하지 않은 것을 됐다고 보고하지 않는다. 테스트가 통과해도 확인 범위가 "로컬"이면 그렇게 쓴다.
- AI 기능(챗봇, 의미로 더 찾기, 자동완성)은 실제 아티팩트에서 한 번 이상 동작을 본 뒤에만 완료로 친다. 자동완성은 지난번에 로컬 테스트만 통과하고 실제로는 안 된다는 보고가 있었다(SPEC 7.3 (f)의 점검 순서).
- 각 기능의 완료 기준을 테스트로 옮긴다. [A]는 Playwright + 로컬 모크(tests/*.spec.cjs), [S]는 Vitest + Playwright. 권한·익명 보호는 테스트로 증명한다.
- 못 한 것, 임시 처리, 환경 때문에 못 돌린 것은 숨기지 않고 SPEC 15장 표와 보고에 적는다.
- 라이브러리·런타임 사용법이 불확실하면 추측하지 말고 공식 문서나 타입 정의를 읽는다([S]는 node_modules/next/dist/docs/, [A]는 아티팩트 기능 문서).

## 아티팩트 제약 체크리스트 ([A] 게시 전에 매번, 자세한 것은 SPEC 4.4)
- db·user·sample·downloads·assets는 모두 null일 수 있다. null이면 그 기능만 숨기거나 이유를 안내하고 화면은 그린다(둘러보기).
- db 경로: 문서=짝수, 컬렉션=홀수 세그먼트. 개인 데이터는 RN.userColl/RN.userDoc 헬퍼로만. 로컬 모크도 같은 규칙으로 TypeError를 낸다. 문서 256KiB 이하.
- 외부 요청 금지. 외부 스크립트는 cdnjs 정확한 버전 URL만. 첫 화면에 필요 없는 것은 필요할 때 불러온다.
- window.print, <a download>, alert/confirm/prompt 쓰지 않는다. 파일 저장은 downloads 기능.
- KaTeX는 output: "mathml"만. trust 금지.
- 소스에 U+FFFD 리터럴 금지(\uFFFD로). 게시 전에 검사한다.
- DOM 헬퍼는 배열을 펴고 null/false를 건너뛴다. 사용자 입력은 innerHTML 금지.
- 예시 데이터는 과거 날짜만. 생성 스크립트에서 검사한다.
- 게시하는 모든 파일은 네가 직접 읽은 텍스트 소스여야 한다. WASM 등 읽을 수 없는 바이너리에 기대는 설계를 하지 않는다(HWP는 자체 파서).
- 휴대폰 폭 400px에서 가로 스크롤 없음, 다크 모드, 색은 CSS 토큰만, 폼 라벨·키보드 조작.

## 병렬 작업 규칙
- 시작 전에 담당표를 만든다: 에이전트별 담당 파일(예: mod-*.js 하나씩), 공용 파일(index.html, core.js, CONTRACT.md, [S]의 messages/ko.json·schema.prisma·package.json)의 주인 한 명. 공용 파일이 필요하면 주인에게 요청을 보고로 남긴다.
- 다른 사람 파일은 고치지 않는다. 고쳐야 하면 좁은 Edit(바꿀 부분만)으로, 파일 전체 덮어쓰기 금지.
- messages/ko.json은 배정받은 최상위 키 안에만 추가한다. decisions.md는 맨 아래에 행만 추가하고 번호는 <이름>-1처럼 붙인다. PROGRESS.md는 메인 세션만 고친다.
- 에이전트마다 git worktree(또는 복사본)를 쓴다. 같은 폴더에서 next dev는 하나만 뜨므로 포트를 바꿔도 같은 폴더를 공유하지 않는다. 테스트 DB·포트도 에이전트마다 따로.
- 작업 단위는 작게(사용 한도로 한꺼번에 끊길 수 있다). 끝날 때 보고: 항목별 완료/미완료, 테스트 결과 수, 확인 범위, 변경한 공용 파일, 브랜치와 마지막 커밋.

## 개발 환경 규칙
- 시작할 때 환경을 점검해 docs/decisions.md에 적는다: 네트워크로 닿는 곳(패키지 레지스트리 외), Docker 데몬, Chromium/Playwright, PostgreSQL 등. 안 되는 것은 대체하고 "미검증"으로 남긴다.
- 대화형 명령을 쓰지 않는다(예: prisma migrate dev 대신 마이그레이션 파일 작성 + prisma migrate deploy). playwright install 등 큰 다운로드는 필요할 때만.
- 커밋 전에 git diff --cached --stat으로 확인한다. 1MB가 넘는 바이너리(wasm, whl, tar.gz, 샘플 문서)는 커밋하지 않고 .gitignore에 넣는다. 제3자 샘플 파일은 내려받는 스크립트로.
- 저장소 안에 다른 저장소 클론을 두지 않는다(타입 검사·린트가 깨진다). 필요하면 바깥 폴더.

## 금지 사항
- 비밀 값(API 키, DB 비밀번호, AUTH_SECRET 등)을 코드·저장소·채팅·로그에 넣지 않는다. 새 환경변수는 .env.example에 이름과 설명만.
- AUTH_TEST_MODE, AI_FAKE를 운영 구성에서 켜지 않는다(AUTH_TEST_MODE는 누구나 아무 계정으로 로그인하게 만든다). 운영 구성 파일에서 강제로 끈다.
- 읽지 않은 파일을 게시하지 않는다.
- 확인하지 않은 것을 됐다고 보고하지 않는다.
- AI 모델 ID를 코드에 하드코딩하지 않는다([S]는 환경변수, [A]는 sample의 modelTier). AI API 키는 서버에서만.
- SPEC에 없는 기능을 임의로 추가하지 않는다. 고충 댓글을 다시 만들지 않는다.
- 사이트에 없는 연구를 AI가 있다고 말하게 두지 않는다. 그래프·통계 수치는 AI가 아니라 코드로 계산한다. 문서 변경은 사용자가 "삽입"/"Tab"을 눌렀을 때만.
- 특정 사람의 이름·이메일·계정, 실제 배포 주소의 식별자(아티팩트 주소, 데이터베이스 프로젝트 ID 등)를 문서·코드·커밋에 넣지 않는다.
